# 회원 탈퇴 구현 가이드 (Soft Delete)

---

## 1. Hard Delete vs Soft Delete

| 방식 | 설명 | 단점 |
|------|------|------|
| **Hard Delete** | DB에서 행을 물리적으로 삭제 | 복구 불가, 분쟁 시 데이터 없음 |
| **Soft Delete** | `deleted_at` 컬럼에 시간만 기록, 데이터는 유지 | 용량이 약간 더 사용됨 |

실무에서는 **Soft Delete**를 사용해요.  
이유: 분쟁/환불/통계 때 데이터가 필요하거나, 일정 기간 내 재가입 복구 기능을 위해서예요.

## 2. 백엔드 구현

### 2-1. `UserEntity` — `deletedAt` 컬럼 + `@Where` 추가

```java
@Entity
@Table(name = "users")
@Where(clause = "deleted_at IS NULL")  // ← 핵심! 모든 조회에서 탈퇴 유저 자동 제외
public class UserEntity implements UserDetails {

    // ... 기존 필드들 ...

    @Column(name = "deleted_at")
    private LocalDateTime deletedAt;  // null = 활성 유저 / 값 있으면 탈퇴 유저
}
```

`@Where(clause = "deleted_at IS NULL")` 하나만 붙이면  
로그인, 파일 조회 등 **모든 쿼리에서 탈퇴 유저가 자동으로 제외**돼요.  
다른 코드를 따로 수정하지 않아도 됩니다.

`ddl-auto = update` 설정이면 앱 재시작 시 `deleted_at` 컬럼이 자동 추가돼요.

---

### 2-2. `UserService` — withdraw 메서드 추가

```java
@Transactional
public void withdraw(Long userId) {
    UserEntity user = userRepository.findById(userId)
            .orElseThrow(() -> new RuntimeException("유저 없음"));

    user.setDeletedAt(LocalDateTime.now());  // 삭제 대신 시간만 기록
    userRepository.save(user);

    // 파일은 그대로 유지
    // → 재가입 시 복구 가능하게 하거나, 배치로 나중에 삭제
}
```

---

### 2-3. `UserController` — 탈퇴 엔드포인트 추가

```java
@DeleteMapping("/users/me")
public ResponseEntity<Void> withdraw(Authentication authentication) {
    if (authentication == null) {
        return ResponseEntity.status(401).build();
    }
    UserEntity user = (UserEntity) authentication.getPrincipal();
    userService.withdraw(user.getId());
    return ResponseEntity.ok().build();
}
```

---

### 2-4. (선택) 배치 스케줄러 — 30일 지난 탈퇴 유저 완전 삭제

```java
// 매일 새벽 3시 실행 — 30일 이상 지난 탈퇴 유저 Hard Delete
@Scheduled(cron = "0 0 3 * * *")
public void hardDeleteWithdrawnUsers() {
    LocalDateTime cutoff = LocalDateTime.now().minusDays(30);
    userRepository.deleteByDeletedAtBefore(cutoff);
}
```

## 3. 프론트엔드 구현 (settings.tsx)

### 탈퇴 플로우

```
"회원 탈퇴" 버튼 (빨간색, 로그인 시에만 표시)
    ↓
1차 Alert — "탈퇴 시 모든 데이터 삭제, 복구 불가" 경고
    ↓
2차 Alert — "정말 탈퇴합니까?" 최종 확인
    ↓
DELETE /users/me 호출 (Authorization 헤더 포함)
    ↓
성공 → logout() 호출 (AsyncStorage 토큰 삭제 + 상태 초기화)
    ↓
"탈퇴 완료" 알림 표시
```

### 핵심 코드

```tsx
const handleWithdraw = () => {
  Alert.alert(
    "회원 탈퇴",
    "정말로 탈퇴하시겠어요?\n\n탈퇴 시 모든 데이터가 삭제되며\n복구가 불가능합니다.",
    [
      { text: "취소", style: "cancel" },
      {
        text: "탈퇴하기",
        style: "destructive",
        onPress: () => {
          Alert.alert("마지막 확인", "정말 탈퇴하시겠어요?\n모든 책 기록, 별점, 읽기 기록이\n영구적으로 삭제됩니다.",
            [
              { text: "취소", style: "cancel" },
              { text: "네, 탈퇴합니다", style: "destructive", onPress: withdrawAccount },
            ]
          );
        },
      },
    ]
  );
};

const withdrawAccount = async () => {
  const token = await AsyncStorage.getItem("accessToken");
  const deviceId = await getDeviceId();

  const res = await fetch(`${BASE_URL}/users/me`, {
    method: "DELETE",
    headers: {
      "X-Device-Id": deviceId,
      ...(token && { Authorization: `Bearer ${token}` }),
    },
  });

  if (res.ok) {
    await logout();  // 토큰 삭제 + 상태 초기화
    Alert.alert("탈퇴 완료", "그동안 이용해 주셔서 감사합니다.");
  }
};
```

## 4. 탈퇴 후 데이터 상태 분석

### 탈퇴 전: 로그인 시 파일 연결 상태

로그인하면 `linkDeviceToUser`가 실행되어 게스트 파일이 유저에 연결돼요:

```sql
UPDATE files SET user_id = 42 WHERE device_id = 'abc123' AND user_id IS NULL
```

```
files 테이블
┌────┬────────────┬───────────┬─────────┐
│ id │ title      │ device_id │ user_id │
├────┼────────────┼───────────┼─────────┤
│  1 │ 팔려간몸.epub │ abc123   │   42    │ ← user_id 있음
│  2 │ 어린왕자.epub │ abc123   │   42    │ ← user_id 있음
└────┴────────────┴───────────┴─────────┘
```

---

### 탈퇴 후: 게스트로 사용할 때 파일이 보이는가?

앱이 게스트 상태에서 파일 조회하는 쿼리:

```sql
SELECT * FROM files
WHERE device_id = 'abc123'
  AND user_id IS NULL    ← user_id가 42이므로 조건 불일치
```

→ **결과 없음 ✅ 파일 안 보임**

---

### `@Where(deleted_at IS NULL)` 이 영향을 주는 범위

| 쿼리 | 영향? | 이유 |
|------|-------|------|
| 로그인 (`findByEmail`) | ✅ 영향 | `UserEntity` 조회 → 탈퇴 유저 로그인 불가 |
| 게스트 파일 조회 | ❌ 영향 없음 | `FileEntity` 조회, `UserEntity` 미사용 |
| 로그인 유저 파일 조회 | ❌ 영향 없음 | `user_id`로 직접 조회 |
| 폴더 조회 | ❌ 영향 없음 | `FolderEntity` 조회 |

## 5. 탈퇴 후 재가입 시나리오

### 현재 구현 기준 (파일 유지, 재연결 없음)

```
탈퇴 → deleted_at = 현재시간
재가입 → 새 user_id 발급 (예: 99)
       → 예전 파일들(user_id=42)은 연결 안 됨
       → 파일 복구 불가
```

### 재가입 시 데이터 복구 원하면 (추가 구현)

```java
// 재가입 시 같은 이메일이면 deleted_at 초기화
UserEntity existing = userRepository.findByEmailIncludeDeleted(email);
if (existing != null && existing.getDeletedAt() != null) {
    existing.setDeletedAt(null);  // 복구
    existing.setPassword(newEncodedPassword);
    return userRepository.save(existing);
}
```

단, 이 경우 `@Where` 조건을 무시하는 별도 쿼리가 필요해요:
```java
// Repository에 추가
@Query("SELECT u FROM UserEntity u WHERE u.email = :email")  // @Where 무시
Optional<UserEntity> findByEmailIncludeDeleted(@Param("email") String email);
```

## 6. 전체 흐름 요약

```
[프론트] 탈퇴 버튼 클릭
    ↓
[프론트] 2단계 경고 Alert
    ↓
[프론트] DELETE /users/me (Authorization 헤더 포함)
    ↓
[백엔드] UserEntity.deletedAt = NOW() 저장
    ↓
[백엔드] 200 OK 반환
    ↓
[프론트] logout() — AsyncStorage 토큰 삭제, user 상태 null
    ↓
[이후 로그인 시도] @Where 조건으로 조회 안 됨 → 로그인 불가
[이후 게스트 파일 조회] user_id IS NULL 조건 불일치 → 파일 안 보임
[30일 후 배치] 물리적으로 완전 삭제 (선택)
```
